The direct answer

The model sees all 83, every time, on every forward pass — including the zeros. There is no feature selection or masking of the input at inference. x is always a dense 83-length vector; every one of those 83 numbers gets multiplied by its own weight column in every linear layer. A zero isn't "skipped" — it's a real value that happens to contribute nothing to that particular dot product (weight × 0 = 0), exactly the way any other number would contribute weight × value.

What is masked is target data during training, not input features during inference — a completely different mechanism, covered in section 09.

07

So what actually gets masked?

Not the input, and not at inference time. Masking happens to targets, during training, per row, per head:

  • Head B (trajectory) is only trained on rows with real Kalshi tick data (has_market_data=1) — basketball-only rows still run through Head B's forward pass and produce an output, it's just excluded from the loss and never influences that head's weights for that row.
  • Heads A and C are masked to rows that have a computed run target.
  • All of this masking lives in trainer.py's loss function, operating on which rows count toward which head's gradient. It has nothing to do with which of the 83 feature columns a given row uses — every row, in training and in inference, always uses all 83.

The zero-filling you see for missing pregame/lineup/market blocks is a data-engineering choice — "no data" is represented as 0 plus a flag bit, not as a differently-shaped input. The network then has to learn to interpret "0 and flag=0" as absence rather than a true measured zero, purely from training signal. There's no architectural mechanism forcing that interpretation — it's an emergent, learned behavior, which is worth remembering as a limitation.
