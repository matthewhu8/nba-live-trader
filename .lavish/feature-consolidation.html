01

Time scaling: use √ remaining, not linear elapsed

Your instinct is right and there is a principled form for it rather than an arbitrary exponential. If in-game scoring is approximately a random walk, the standard deviation of the remaining margin swing scales with √m (minutes remaining). So a lead of d is worth:

lead_z = score_diff / sqrt(max(m, 0.5)) # signed, in units of "remaining randomness"

This is the standard win-probability construction. It keeps the sign, amplifies late (exactly your 40→45 vs 10→15 point), and subsumes three existing columns at once.

A separate nonlinear clock

Score-independent time pressure still deserves its own column, on the same √ scale:

time_leverage = 1 - sqrt(m / 48) # 0.0 at tip-off → 1.0 at the buzzer
Five minutes of game timeLinear minutes_into_game/48Proposed time_leverage

Same five minutes of clock, 2.6× the input resolution when it is three minutes left instead of eight. That is the property you asked for, and q4_close_game becomes redundant: "close game, late" is just small |lead_z| with high time_leverage, expressed continuously instead of as a hard conjunction at one threshold.

Net effect on this block

7 columns → 4. score_diff, lead_z, time_leverage, garbage_time_risk. Dropped: period (recoverable from time_leverage), minutes_into_game, trailing_team_urgency, comeback_probability_proxy, q4_close_game.

02

The other seven groups

Same two moves throughout: fold direction into magnitude, and decorrelate nested windows by expressing the second one as a difference from the first.

Runs · 5 → 3

run_signed_points = sign(run_team) * current_run_points # direction folded in run_efficiency = current_run_points / max(current_run_length, 1) run_fragility = current_run_3pt_pct - current_run_paint_pct # + = jumper-driven = reverts

run_length and run_points correlate heavily (a k-possession run is roughly 2.3k points), so feeding both raw is mostly duplicated variance; the ratio is the orthogonal part. run_fragility encodes the finding already in the memory notes that 3pt-heavy runs revert.

Recent scoring · 4 → 2

swing_5 = home_points_last_5 - away_points_last_5 swing_accel = swing_5 - (swing_10 - swing_5) # recent half vs prior half

The 5 and 10 windows are nested and correlate ~0.7. Expressing the second as an acceleration decorrelates them instead of feeding the same trend twice.

Shot quality · 8 → 3

xppp_edge = home_xPPP_last_5 - away_xPPP_last_5 luck_edge = home_actual_vs_expected_PPP - away_actual_vs_expected_PPP quality_trend_edge = (home_xppp_5 - home_xppp_prev5) - (away_xppp_5 - away_xppp_prev5) # RAW, not sign()

luck_edge is the highest-value feature in this whole proposal and the closest to the core thesis: a team scoring above its shot quality is due to regress, and the market is watching the scoreboard rather than the shot chart. Drop scoring_sustainable entirely — it is a thresholded copy of the same rolling xPPP.

Pace · 2 → 2, restructured DATA ALREADY EXISTS

Your shrinkage idea, with the plateau you specified:

w = min(0.85, elapsed_poss / (elapsed_poss + 40)) pace_ref = w * pace_game_to_date + (1 - w) * expected_pace pace_surprise = pace_last_10 - pace_ref
  • Early: w is small, the prior dominates — correct, the in-game sample is tiny.
  • At 40 elapsed possessions: w = 0.5, an even blend.
  • Late: w ceilings at 0.85, never 1.0 — the prior keeps a floor of influence, exactly as you described.
Decision 2 resolved at zero cost

You asked for a real per-team season pace prior. It already exists and is already wired into both paths. expected_pace (feature_config.py:91) is built in pregame_features.py:207 as the mean of the two teams' avg_secs_per_poss from features.team_ratings.

It is already lookahead-safe. The query filters WHERE g.game_date < game_date ORDER BY g.game_date DESC LIMIT 1 (pregame_features.py:186-188) — strictly prior games, as-of the game being predicted. No new ingestion, no new audit surface.

Better still: this formula structurally fixes parity bug #4, because it names both the within-game mean and the pregame prior explicitly with a defined weight. Today one path uses one and the other path uses the other.

Honest accounting

First-layer parameters drop from 16,683 to 11,658 — about 13.5% of the 37K model. That is real but modest, and it is not the main argument.

The main argument is conditioning: removing four exactly-collinear relationships, recovering sign on five directional quantities, and repairing two scale defects that are currently destroying features outright. Fewer columns is a side effect, not the goal.

04

Decision: hybrid, built now

Decided · Option C

Fixed formulas for the physics groups; a learned bottleneck for the 14 market columns; both in this pass.

Concretely, that means the 33 physics features are computed as closed-form numpy in the feature pipeline exactly as specified above, while the market block keeps all 14 raw columns and gains a small trainable encoder in front of the experts:

market_encoder = nn.Linear(14, 4) # ~60 params, trained end-to-end x = concat([physics_33, pregame_11, market_encoder(market_14)]) # 48-dim expert input

The reasoning holds up: you have strong domain priors about basketball physics (a lead is signed, home minus away is the directional quantity, jumper-heavy runs revert) and essentially none about how yes_bid, spread, open_interest, and bid_velocity_30s should combine. Spend parameters where the prior is weak, spend formulas where it is strong.

One refinement worth taking

Building C now costs the clean physics-only baseline, which means a metric move in the final batch cannot be attributed between "the physics consolidation worked" and "the market encoder worked."

That attribution is recoverable for one extra retrain: land the physics consolidation as batch 3, then the market encoder as batch 4. Same destination, same code, one more training run, and you learn which half paid. Recommended, but it is your call and the sequencing below shows both.

05

The prerequisite: one shared transform module

Every feature exists twice: offline in models/features/*.py (pandas, whole-game, vectorized) and online in live-trader/inference/features.py (streaming, per-possession). We have now found four parity bugs across two small blocks. Consolidating into richer derived features multiplies that risk unless the derivation itself is shared.

Because the transforms are pure numpy, the same function serves both callers: arrays offline, scalars online. Add a parity test that pushes identical raw state through both paths and asserts agreement to 1e-6. That test would have caught all four bugs below.

06

Sequencing: three batches

Per your decision. All three are now written and tested; the retrains are the remaining step and are yours to run.

A test was enforcing bug #3

tests/test_garbage_gate.py::test_model_feature_constants_frozen asserted _TRAIN_BLOWOUT_MARGIN_PTS == 30 and called those values "the training definition". They never were — training used a sigmoid centred on a 15-point margin. The test was pinning the divergence in place and would have blocked the fix.

It now asserts the opposite: that the live module carries no local copy of those constants, and that the model input is continuous and monotone in margin.

Batch 1Correctness — no retrain, no feature changes
  • Fix all four parity bugs. Live is wrong and training is right in every case; this is a live-only fix.
  • Extract models/features/transforms.py and route both paths through it. No behavior change.
  • Add the parity test asserting offline == online to 1e-6.
  • Confirm the feature store rebuilds bit-identical.

Gate: nothing below starts until the parity test is green.

Batch 2Scale defects + collinearity drops — one retrain
  • 999 sentinel → bounded min(x, 30) plus explicit no_timeout_yet flag.
  • np.sign() → raw difference on shot_quality_trend; drop scoring_sustainable.
  • Drop the seven exactly-collinear columns.
  • Rename pace_season_baseline → pace_game_to_date.

Expectation: the collinearity drops are lossless by construction. Any degradation means the collinearity analysis is wrong and batch 3 is suspect.

Batch 3All sign-folding + consolidation + market encoder — one retrain
  • All seven consolidation groups at once: 58 → 33 physics.
  • lead_z, time_leverage, pace shrinkage toward expected_pace.
  • Market encoder nn.Linear(14, 4) in front of the experts.

Optional split (recommended): hold the market encoder back as batch 4. One extra retrain buys you the physics-vs-market attribution you otherwise lose here.

Risks
  • The current backtest is invalidated. 207 trades / 47.8% win rate / +$37,409 was measured on the current feature set. All of it must be re-validated before this touches paper trading, let alone real money.
  • The 2024-25 test set stays sacred. Every decision above comes off validation only.
  • Judge per head, not on aggregate. Sign folding should help Head B (directional, 61.1%) most. Heads A and C may not move, and an aggregate metric would hide that.
  • Batch 3 is the attribution risk you accepted. Seven groups plus an architecture change in one retrain. If it degrades, the only way back is to bisect, which costs more than the batches you saved.
  • Bug 4 means live pace behavior has never matched training. Any historical live or paper result that depended on pace features was produced by a model reading a constant where it was trained on a curve.
