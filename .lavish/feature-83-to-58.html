From 83 raw inputs to a 48-dim expert vector

Two separate steps, run by two separate mechanisms. Step 1 is offline, deterministic, hand-written math (models/features/transforms.py) that shrinks 83 columns to 58. Step 2 happens live inside the model — a single learned linear layer that shrinks the 14 market columns to 4, giving the experts 48 numbers to work with.

Original inputs
83
58 physics + 11 pregame + 14 market
After hand-consolidation
58
33 physics + 11 pregame (unchanged) + 14 market (unchanged)
After the learned encoder
48
44 pass through + 14 market → 4 (nn.Linear)
Only the physics block was hand-consolidated. Pregame (11) and market (14) columns are the exact same columns before and after — market just gets compressed later, by a trained neural layer instead of a formula, because nobody has a confident hand-written formula for how bid/ask/spread/volume should combine.

Pregame block — 11 → 11 (unchanged)

no consolidation

These are one-time, per-game numbers computed before tip-off from each team's trailing form. None of them were touched by the consolidation — every one of the 11 columns below is read as-is, joined onto every possession row by game_id.

Market block — 14 raw → 4 learned

learned, not hand-written

The 14 raw columns themselves are untouched — no formula runs on them the way physics features get combined. Instead, all 14 are fed through one small trained layer that learns its own 4-number summary during training.

#ColumnGroupWhat it is
1yes_bidRaw LOB stateCurrent best bid on YES
2yes_askCurrent best ask on YES
3spreadyes_ask − yes_bid
4yes_lastLast traded price
5open_interestOpen contracts outstanding
6trade_volume_60sLiquidity regimeRolling 60s sum of traded volume
7time_since_last_trade_msMilliseconds since the last volume > 0 tick
8open_interest_change_60sΔ open interest over the last 60s
9d_yes_bidPrice velocityChange from previous possession's tick
10d_spreadChange in spread from previous possession's tick
11bid_velocity_30s(bid_now − bid_30s_ago) / 30
12bid_acceleration_30svelocity_now − velocity_30s_ago
13bid_vs_last_divergenceDivergence / flagyes_bid − yes_last (stale-order detection)
14has_market_data1 if a Kalshi tick exists for this row, else 0

The learned function: nn.Linear(14, 4)

Each of the 4 output numbers is a plain weighted sum of all 14 market inputs, exactly the "one neuron" mechanic from earlier — no activation function is applied at this step, it's purely linear:

for each output i in 1..4: encoded[i] = b[i] + Σ_(j=1..14) W[i][j] · market_raw[j] W is a 4×14 matrix of learned weights → 56 numbers b is a 4-length vector of learned biases → 4 numbers Total learned parameters in this layer: 56 + 4 = 60

There is no formula to show for what W and b actually are — unlike every physics feature below, these 60 numbers aren't hand-derived. They start random and are adjusted by backpropagation, alongside every other weight in the network, to whatever values minimize the combined Head A / B / C loss on the training set. That's the literal meaning of "learned": the transformation exists, but no one wrote down what it computes — training found it.

Physics block — 58 → 33 (hand-consolidated)

deterministic formulas

This is the block that actually shrank. All 33 replacement values are computed by named functions in models/features/transforms.py — plain numpy math, no training involved. Three repeating problems drove the shrinkage, and every subgroup below is an instance of one or more of them:

Problem 1

Direction + magnitude split across two columns when one signed number says the same thing — forces the network to learn a multiplication it's bad at from limited data.

Problem 2

Exact algebraic duplicates — one column was 100% derivable from others already present (e.g. in_bonus == (fouls_until_bonus == 0)), so it added weights without adding information.

Problem 3

Broken encodings — a 999 sentinel value crushed a 0–70 range into a 0.24-wide z-score band; np.sign() quantization threw away real magnitude.

A. Score × time 7 → 4
Old (7)
score_diffperiod minutes_into_gametrailing_team_urgency comeback_probability_proxyq4_close_game garbage_time_risk
New (4)
score_difflead_z time_leveragegarbage_time_risk
score_diff = unchanged, passed through lead_z = score_diff / sqrt( max(minutes_remaining, 0.5) ) # replaces trailing_team_urgency (|d|/m) and # comeback_probability_proxy (d²/m) — both threw away # the sign, so +6 with 1 min left and −6 with 1 min # left looked identical to the model. time_leverage = 1 − sqrt( clip(minutes_remaining_raw / 48, 0, 1) ) # sqrt-scaled clock: replaces the linear # minutes_into_game AND the hard 0/1 threshold # q4_close_game with one smooth curve that gives # late-game minutes more resolution than early ones. garbage_time_risk = sigmoid( (|score_diff| − 15) / 5 ) · clip(1 − minutes_remaining_raw/48, 0, 1) # same formula as before, just centralized so live # and training compute it identically.
clip(x, lo, hi) in proper math notation is min(max(x, lo), hi) — take x, but never let it go below lo or above hi. So clip(minutes_remaining_raw / 48, 0, 1) = min(max(minutes_remaining_raw / 48, 0), 1): the ratio is computed normally, then floored at 0 and capped at 1 so it can never leave the 0–1 range the sqrt() right outside it needs. This same clip shows up again below in garbage_time_risk, fouls_until_bonus, full_timeouts_remaining, and poss_since_timeout — same min(max(·)) meaning every time.

period is still used as a raw input inside these formulas, it's just no longer handed to the network as its own separate column.

weight(elapsed) = min( elapsed / (elapsed + 40), 0.85 ) # weight on the in-game pace mean; starts near 0 (trust the # pregame prior), climbs toward 0.85 by ~40 possessions, and # plateaus there so the prior always keeps a floor of influence pace_ref = weight · pace_game_to_date + (1 − weight) · expected_pace # expected_pace is the PREGAME feature (block above) — this is # the one place a physics formula reaches into another block. # An empirical-Bayes blend of "what this game has actually # looked like so far" and "what we expected coming in". pace_surprise = pace_last_10_possessions − pace_ref # how much faster/slower the last 10 possessions ran than # the blended reference.

Count didn't shrink here (2→2), but the formula did change — pace_season_baseline (a raw running average) was replaced by pace_ref, a properly shrunk blend that pulls in the pregame prior.
