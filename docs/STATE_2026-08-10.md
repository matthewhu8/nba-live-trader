## 1. What changed

`models/targets/exit_simulator.py::build_trajectory_targets` anchored every offset at each
possession's `wall_clock_ts`, while `yes_bid` on the same row came from the asof join at
`wall_clock_ts + feed_delay_seconds` (`dataset.py:680`). The labels were **anti-causal, not
merely early**: TP and SL resolved against ticks that preceded the price the position entered
at, so Head B learned to expect fills that were already in the past.

| change | file | effect |
|---|---|---|
| Anchor at `wall_clock_ts + feed_delay_seconds` | `exit_simulator.py` | fixes both `future_*` filters, the checkpoint grid and the time gate from one name |
| `feed_delay_seconds` is **required**, no default | `exit_simulator.py` | omitting it *was* the defect; a new call site must state it |
| Pass the join's delay through | `dataset.py:1003` | entry price and exit window can no longer be anchored at different moments |
| TP clamp moved inside `simulate_exit` | `exit_simulator.py` | post-exit checkpoints freeze at the collectable price, not the overshoot |
| Clamp deleted from the call site | `mmoe_backtest.py` | was duplicated; behaviour unchanged |
| Head B comparability instrumentation | `trainer.py` | see §4 |
| TP clamp to `effective_tp` | `dynamic_exit.py` | same defect 2, third instance; `effective_tp` not `tp` because the streak rule re-posts the limit further out |
| `take_profit_widened` added to `_MAKER_EXIT_REASONS` | `mmoe_backtest.py` | a widened TP still rests; the sweep was charging 4x taker on it |

The horizon is now a **true `horizon_seconds` from entry**. It was `wall_clock_ts + horizon`,
i.e. 100s of real hold at a 20s delay, which also meant stops in the final 20s were labelled
flat `time_gate` exits.

## 4. Head B's metrics are not comparable across this change

The full argument is in `skills/model-provenance.md`. The short version, because the
temptation to retrain and check whether `loss_b` improved is the one wrong move available:

`trainer.py::_compute_loss` masks Head B to rows where `mean |traj| > 0.02` — a threshold on
the labels themselves. The anti-causal early TP/SL hits were the high-magnitude rows that
cleared it, so **both the target values and the row population moved**. `loss_b` is now an
average of a different quantity over a different set of rows. Head B can post a *better*
`loss_b` purely by being scored on fewer, easier rows. And since selection is on total val
loss, `loss_b`'s scale change shifts which epoch is kept, so Head A's and Head C's numbers
are individually well-defined but *which checkpoint you have* is not.

Instrumentation added to make the comparison recoverable — `head_b_rows` /
`head_b_rows_total` (mask retention), `rmse_b_zero` (predict-nothing reference, logged as an
`RMSE_B/zero-pred` ratio), `rmse_b_per_checkpoint` (logged beside each saved checkpoint).

**Head C was never affected.** `CLAUDE.md`, `data-integrity.md` and the 2026-08-05 state all
said the simulator built "Head B and Head C" labels. Head C's hazards come from
`kalshi_targets.add_hazard_targets`, indexed over the next N *scoring possessions* rather than
wall clock, and never touch the exit simulator. Only `traj_0..9` moved. All three corrected.

## 4b. Code review found three real defects in the above

Reviewed after the first commit (`eb2b951`). Three findings were confirmed and fixed in
`4d8ba0e`; three more are open and listed in §5.

**1. Clamping `exit_price` did not close the overshoot leak.** Checkpoints at or before the
exit are looked up *forward*, so whenever no tick falls between a checkpoint and the breach
they resolve to the breaching tick and carry its uncollectable price. Measured: entry 50c,
ticks at +10s (50c) and +30s (64c), tp=5 → `exit_price` correctly clamped to 55, but `traj_0`
and `traj_1` both reported `logit_delta(50, 64) = 0.5754` against the collectable `0.2007`.
The commit's own test could not see it — with a 20s delay the exit landed at offset 10, so
every checkpoint took the post-exit frozen path. Now capped on take-profit paths, with a test
that fails when the cap is reverted.

**2. The `RMSE_B/zero-pred` ratio compared different row populations.** `rmse_b` is computed
over `mkt_mask`, `rmse_b_zero` over the narrower `head_b_mask`, so the reference saw only
large-target rows while the numerator was diluted by the ~42% of market rows with ~0
trajectory. Demonstrated: a model predicting **exactly zero** everywhere printed a ratio of
**0.762** — reading as "beats predicting nothing by 24%" — where the corrected
`rmse_b_masked / rmse_b_zero` prints **1.000**. This is the metric added to stop exactly that
misreading, so it would have failed in the one situation it exists for.

**3. `feed_delay_seconds` was positionally bindable.** As the 4th positional parameter, a call
written against the old signature — `build_trajectory_targets(rows, ticks, poss, 5.0, 3.0)` —
silently bound `feed_delay_seconds=5.0` and `tp=3.0`, and `pd.Timedelta` accepts the float. Now
keyword-only, which is what "required so a caller has to state it" was supposed to buy.

Also fixed: a stale comment at `mmoe_backtest.py` claiming `exit_price` was caller-clamped,
which would have invited re-adding the removed clamp.

### Original finding: Level 2 does NOT cover possession-driven exit timing

**And this state file's §1 overclaimed, as did my rewrite of `data-integrity.md`, which deleted
a still-valid warning. Both corrected.**

Level 2 fixed the entry anchor, which governs which possessions the exit search can *reach*. It
did not delay the possession *events*. `simulate_exit` still compares raw possession wall clock
against tick time, so a momentum flip is acted on the moment its wall clock passes rather than
`feed_delay_s` later. Measured: entry anchored `T0+20`, flip at possession wall clock `T0+30`,
tick at `T0+35` → `momentum_flip` at `T0+35`, though it is not knowable until `T0+50`.
`dynamic_exit` shares the shape, and also gates re-inference on it.

**`momentum_flip` is 32.6% of baseline exits, so fixing this moves −$324.35.** That makes it a
modelling decision, not a measurement patch, and it is deliberately left for a scoped call. The
sign is not predictable: firing early is sometimes favourable. The trigger belongs at
`wall_clock_ts + feed_delay_s` in **both** simulators at once, or the label path and the sweep
path diverge on exit timing.

### Still open, lower severity

1. **`dynamic_exit` can widen past an already-fillable limit.** The possession loop runs before
   the TP check *on the same tick*, so at entry 50c / tp=5, a tick printing 56c that also
   crosses a possession boundary can widen `effective_tp` to 8 and then fail the `move >=
   effective_tp` test — the resting order at 55c was live and would have filled. The clamp is
   still an improvement over booking `current_bid`, but it now writes that fiction into P&L.
   Widening should take effect from the next tick, or be skipped when `move >= tp` already
   holds. Sweep-only, and pre-existing.
3. **The widened-TP clamp has no end-to-end test** (needs a predictor stub plus a full
   possession row through `_build_feature_dict`). It clamps on the same line as the base case.
